# REQUIREMENT: 报警图片二次校验平台

- **Change ID**: alarm-image-verify
- **关联**: `@.specs/alarm-image-verify/CHANGE.md`、`@.specs/CONTEXT.md`

---

## 用户故事

- **US-1**：作为上游告警程序，我想通过 WebAPI 同步提交报警图片与报警 bbox JSON，以便立即拿到二次识别的类别与置信度，用于降误报参考。
- **US-2**：作为投递方，我想把图片与同名 sidecar JSON 放入指定目录，以便平台定时拉取并完成二次识别、结果可查。
- **US-3**：作为审核人员，我想在 Web 日志台查看任务列表与详情（原图、原告警 bbox、二次识别结果），以便事后核对，且不能改写系统判定。

## 验收准则（AC）

### AC-1 · 同步 API 入图并返回识别结果

- **Given** 平台服务已启动且二次识别能力可用
- **When** 上游以约定接口提交一张报警图片 + 报警 bbox JSON
- **Then** 响应成功，且 body 中包含至少一条检测结果，每条含 `label`（类别）与 `confidence`（置信度，0~1）；同时该次调用对应任务已落库
- **验证方式**: 手动或脚本 `POST` 入图接口一次，检查 HTTP 成功与响应字段；再在日志台或查询接口确认任务存在

### AC-2 · API 缺少必要入参时明确失败

- **Given** 平台服务已启动
- **When** 请求缺少图片，或缺少/无法解析 bbox JSON
- **Then** 返回 4xx，响应说明错误原因；不产生「识别成功」任务记录
- **验证方式**: 分别发送缺图、缺 JSON 的请求，断言状态码与错误信息

### AC-3 · 目录 sidecar 入图

- **Given** 监视目录已配置，服务正在定时扫描
- **When** 向该目录放入成对文件 `foo.jpg`（或常见图片后缀）与 `foo.json`（含 bbox）
- **Then** 在约定扫描周期内生成对应任务，完成二次识别，结果含类别与置信度，并可在日志台看到该任务
- **验证方式**: 投放一对 sidecar 文件，等待不超过文档约定的扫描周期上限，在日志台确认任务与结果

### AC-4 · 目录仅有图片无 sidecar 时不误报成功

- **Given** 监视目录已配置
- **When** 仅放入 `bar.jpg` 而无 `bar.json`
- **Then** 不产生「识别成功」任务；可有可观测的跳过/待补全记录或日志（具体形态 DESIGN 定），但不得当作校验完成
- **验证方式**: 只投图片，等待至少一个扫描周期，日志台无成功任务；检查服务日志有对应提示

### AC-5 · 审核日志台 · 任务列表

- **Given** 系统中至少存在 1 条已完成的校验任务
- **When** 审核人员打开日志台列表页
- **Then** 能看到任务条目（至少含任务标识、创建时间、处理状态）；列表为只读，无「改判/覆盖结果」操作
- **验证方式**: 手动 UAT：打开列表页截图/操作确认

### AC-6 · 审核日志台 · 任务详情对照

- **Given** 某任务已完成二次识别
- **When** 审核人员打开该任务详情
- **Then** 可同时看到：原图、原告警 bbox 叠加（或等价对照展示）、二次识别的类别与置信度（及二次框若模型产出）；详情页无保存/覆盖判定的写操作
- **验证方式**: 手动 UAT：打开详情核对三要素；确认无改判控件

### AC-7 · 识别结果可被上游在同步响应中直接消费

- **Given** AC-1 的成功响应
- **When** 上游解析响应 JSON
- **Then** 无需再调回调或 Webhook 即可获得本次二次识别的类别与置信度；v1 不要求平台主动回写上游
- **验证方式**: 与 AC-1 同一响应断言；代码/契约中不存在 v1 回写上游的必选步骤

## 范围切分

### v1（本次必做）

- 同步 WebAPI：图片 + bbox JSON → 类别 + 置信度，并落库
- 指定目录定时扫描：同名 sidecar（`*.jpg|png|…` + `*.json`）
- 任务与结果持久化
- 审核日志台：任务列表 + 详情（原图 / 原告警 bbox / 二次识别结果），只读
- 工业风 Web UI（调性已在 CHANGE 锁定）

### v2（下一轮考虑，不本次）

- 异步入图（task_id + 查询）与可选 Webhook 回写上游
- 日志台按时间/状态筛选、检索
- 目录 inbox 多种命名策略、失败重试策略可配置化
- 简单 API Key / 访问控制（仍非复杂权限体系）

### out（永远不做）

- 多租户
- 复杂权限体系
- 大盘统计分析
- 移动端
- 人工改判 / 覆盖模型输出作为系统判定
- 模型在线训练产品化

## 非功能性需求

- **性能**: v1 软目标——单张常见分辨率图片同步 API 在模型已加载前提下，P95 端到端 < 5s（不含冷启动）；目录扫描周期默认可配置，默认建议 ≤ 10s。不作为硬 SLA 门禁，TEST 阶段作基线记录。
- **可访问性**: 无强制 WCAG 门禁；日志台须键盘可打开列表/详情，文字与背景对比度可读（工业风深底浅字或等价）。
- **安全**: v1 不做复杂鉴权；默认假设部署在受信网络。上传接口须限制体大小与文件类型（图片 MIME/后缀白名单），防止明显滥用。
- **兼容性**: 日志台支持最近两个大版本的 Chrome / Edge；API 为 HTTP JSON，客户端语言不限。
- **可观测性**: 入图成功/失败、识别耗时、目录跳过原因须有结构化日志；v1 不要求独立监控大盘。

## 依赖与假设

- 依赖可加载的目标检测推理能力（具体框架/模型属 DESIGN；产品名不绑定某一模型品牌）。
- 假设上游 bbox JSON 遵循 `@.specs/CONTEXT.md` 中锁定的 v1 schema（像素坐标 `xywh`）。
- 假设监视目录与平台进程对同一文件系统可见（本地或挂载卷）。
- 假设 v1 单实例部署即可，不做多租户与跨区域。
